# Make these stories render

This folder is a Storybook for the application in this repository, generated by Ocoder. Every
component listed in `ocoder.json` has a story, and every story has an entry in `catalog.json`. The
stories build, and they are wrapped in the providers the app's entry module sets up, but their props
are empty, so many do not render the way the app shows them yet.

Your job is to make every catalog case pass `pnpm run verify`, with stories that show each component
the way the application uses it.

## What done means

`pnpm run verify` exits 0. It builds the Storybook and renders every case in every theme the same
way Ocoder's capture will. A case fails on any of:

- a check in `catalog.json` that is not satisfied
- any console error, including React warnings logged as errors
- any request to another origin, or any WebSocket — there is no network. A component that fetches on
  mount needs its data supplied through props, a provider, or a stub; it cannot reach a server
- any HTTP error from the Storybook itself, a broken image, or web fonts that do not finish loading

Read the failure lines. They carry the error Storybook showed, the blocked URL, or the check that
was not met.

## Files you own

- **`.storybook/providers.tsx`** — wraps every story. It was generated from the app's entry module
  (see `appDir` in `.storybook/target.json`, then its `index.html` and entry script): the app's own
  wrappers in the app's order, with a fresh query client and an in-memory router in place of the
  app's. Wrappers it could not reproduce are listed in a `Left out:` comment and in
  `providers_skipped` in `ocoder.json`; add them if stories need them. `theme` is the capture theme
  (`light` or `dark`); it is set as a `dark` class, `data-theme` and `color-scheme` on `<html>`. If
  the app switches theme some other way, make it render in that theme through the app's own mechanism.
- **`.storybook/stubs/*.tsx`** — stand-ins for auth SDKs (`stubbed_packages` in `ocoder.json`), which
  need a key and a network this sandbox does not have. Every import of the package loads its stub,
  which answers as a signed-in sample user. Extend a stub when a component needs a value it does not
  provide; keep its exports.
- **`stories/*.stories.tsx`** — give each story realistic props. Look at how the application renders
  the component (call sites, tests, existing examples) and use values like those. You may add stories
  for distinct, meaningful states.
- **`fixtures/`** — data your stories import.
- **`catalog.json`** — you may add cases for stories you add, and add checks to existing cases. A good
  check proves the component rendered its real content: text it should show, a count of rows, an
  attribute. Do not weaken or remove the checks that are there.

Import the application's source as `@source/<repository path>`, never with relative paths: this
folder may be built from a different location. Import packages by their normal names.

## Do not change

- `.storybook/main.ts`, `.storybook/target.json`, `package.json`, `pnpm-lock.yaml`,
  `pnpm-workspace.yaml`, `verify.mjs`, `ocoder.json`, this file.
- In `catalog.json`: the `component_key`, `source_binding` and `storybook_story_id` of existing cases,
  and the `target_id`, `viewport` and `themes`.
- Anything outside this folder. The application's source is read-only.

No packages can be installed: dependencies were installed before you started, and the network is
closed. If a component needs a package that is not installed, say so in your final message and leave
that story failing rather than working around it.

When a component cannot be rendered in isolation at all, leave its case failing and say why in your
final message. Do not delete the case.
