# Make these stories render

This folder is a Storybook for the application in this repository, generated by Ocoder. Every
component listed in `ocoder.json` has a story, and every story has an entry in `catalog.json`. The
stories build, and they are wrapped in the providers the app's entry module sets up, but their props
are empty, so many do not render the way the app shows them yet.

Your job is to make every catalog case pass `pnpm run verify`, with stories that show each component
the way the application uses it.

## When this is an update

If `ocoder.json` has a `last_update` section, this folder was generated earlier and has just been
brought up to date with the application. Most of it is finished work, by you or by a person, from a
previous run. Read `last_update` first; it says what changed:

- **`added`** — components that had no story. Each has a new story with empty props and one catalog
  case. These are your main work, as in a first run.
- **`changed`** — components whose source changed since their story was written. The story was kept
  as it was. Its catalog entry was reset to a single case with a single check: the extra cases and
  checks added before were written against the old code and may no longer be possible. Make the
  story render against the component as it is now, then add back the cases and checks that still
  make sense. If the story file has stories that no longer apply, remove them from the file.
- **`removed`** — components that no longer exist. Their stories and cases are already gone; there
  is nothing to do.
- **`entry_module_changed`** — when true, the app's entry module changed since
  `.storybook/providers.tsx` was written from it. The providers were not regenerated. Compare them
  with the entry module and bring them up to date if stories need it.

Leave every other story, check and fixture alone. They passed before and are not part of this
update; do not rewrite or "improve" them. If one of them now fails, that is worth fixing — say in
your final message which and why.

Everything below applies to an update as it does to a first run.

## What done means

`pnpm run verify` exits 0. It builds the Storybook and renders every case in every theme the same
way Ocoder's capture will. A case fails on any of:

- a check in `catalog.json` that is not satisfied
- any console error, including React warnings logged as errors
- any request to another origin, or any WebSocket — there is no network. A component that fetches on
  mount needs its data supplied through props, a provider, or a stub; it cannot reach a server
- any HTTP error from the Storybook itself, a broken image, or web fonts that do not finish loading

Read the failure lines. They carry the error Storybook showed, the blocked URL, or the check that
was not met.

Verify also prints `note:` lines under some cases. A note does not fail the case, but it means the
story probably does not show the component the way the app does: see the next section, and act on
every note you can.

## Files you own

- **`.storybook/providers.tsx`** — wraps every story. It was generated from the app's entry module
  (see `appDir` in `.storybook/target.json`, then its `index.html` and entry script): the app's own
  wrappers in the app's order, with a fresh query client and an in-memory router in place of the
  app's. Wrappers it could not reproduce are listed in a `Left out:` comment and in
  `providers_skipped` in `ocoder.json`; add them if stories need them. `theme` is the capture theme
  (`light` or `dark`); it is set as a `dark` class, `data-theme` and `color-scheme` on `<html>`, and
  passed directly to providers the generator knows need it. If the app has more than one theme and
  switches some other way (a UI library's provider, its own theme provider, a context, a store),
  make it render in the capture theme through the app's own mechanism, then check it: a story of a
  themed component looks different in each theme. Verify does not check this for you. If the app has
  only one theme, leave it: do not add a theme, styles or colours the app does not have, and say so
  in your final message.
- **`.storybook/stubs/*.tsx`** — stand-ins for auth SDKs (`stubbed_packages` in `ocoder.json`), which
  need a key and a network this sandbox does not have. Every import of the package loads its stub,
  which answers as a signed-in sample user. Extend a stub when a component needs a value it does not
  provide; keep its exports.
- **`stories/*.stories.tsx`** — give each story realistic props. Look at how the application renders
  the component (call sites, tests, existing examples) and use values like those. You may add stories
  for distinct, meaningful states.
- **`fixtures/`** — data your stories import.
- **`catalog.json`** — you may add cases for stories you add, and add checks to existing cases. A good
  check proves the component rendered its real content: text it should show, a count of rows, an
  attribute. Do not weaken or remove the checks that are there.

Import the application's source as `@source/<repository path>`, never with relative paths: this
folder may be built from a different location. Import packages by their normal names.

## Components that need a size or a URL

Each story renders its component alone, in a page-sized frame, with the router (if the app has one)
at `/`. Two kinds of component come out wrong that way, and verify notes both.

**A component that takes the size it is given** — an icon with no size of its own, an image, a
full-width bar, a layout shell — fills the whole frame. Verify notes it as "fills the frame". Show
it the size the app shows it:

- If it takes a size (a `size`, `width` or `height` prop, or similar), set it in the story's `args`
  to a value the app uses, so it shows as a control.
- Otherwise give the story a decorator that puts it in a box sized the way the app uses it: look at
  where the app renders it (a 20px icon in a button, a sidebar 260px wide).
- Put the decorator in the story file. Not in `.storybook/providers.tsx`, which wraps every story.

Some components are meant to fill the page, such as a whole page layout. Leave those as they are and
say so in your final message.

**A component that renders pages by URL** — the app's root component, a layout that renders the
current route, a page — shows the app's not-found page when the router is at a URL the app has no
page for. Verify notes it as `shows "Not found"` (or "404"). Render it at a URL the app has, with
the data that page needs:

- Find the app's routes, and pick one that shows the component meaningfully.
- If `Providers` in `.storybook/providers.tsx` takes a `route`, set it per story:
  `parameters: { route: '/settings/profile' }`.
- If it does not, give the story a decorator that moves the router to that URL, with the router's
  own navigation, before rendering the story.
- A component that creates its own router cannot be rendered inside another one. If it is the app's
  root component, write a story for what it renders inside its router instead, if that is a
  component the app exports. Otherwise leave the case failing and say why.

## Catalog format

`pnpm run verify` checks `catalog.json` before it builds, and names every field that is wrong. The
format is strict: an unknown field anywhere is an error.

A case you add for a new story of an existing component copies that component's `component_key` and
`source_binding` exactly, and gets its own `scenario_key`:

```json
{
  "component_key": "copybutton-b757d092",
  "scenario_key": "copied",
  "checkpoint_key": "default",
  "source_binding": {
    "file": "src/components/common/copy-button.tsx",
    "export_name": "CopyButton"
  },
  "storybook_story_id": "components-copybutton--copied",
  "required": true,
  "checks": [{ "kind": "text", "selector": "#storybook-root", "includes": "Copied" }]
}
```

- `component_key`, `scenario_key`, `checkpoint_key` and `storybook_story_id` are lowercase: letters,
  digits, `.`, `_`, `-`. The three keys together are unique in the catalog.
- `storybook_story_id` is Storybook's ID for the story: the title and the story's export name,
  lowercased with `-` between words, joined by `--` (`Components/CopyButton` + `Copied` →
  `components-copybutton--copied`).
- `checks` has 1 to 32 entries, each exactly one of:
  - `{ "kind": "visible", "selector": "…" }`, optionally with `"text": "…"`
  - `{ "kind": "text", "selector": "…", "includes": "…" }`
  - `{ "kind": "count", "selector": "…", "equals": 3 }`
  - `{ "kind": "attribute", "selector": "…", "name": "aria-pressed", "equals": "true" }`
- The only other field a case may have is `capture_selector`. Do not add descriptions, titles or
  comments to the catalog.

## Do not change

**Anything not listed under "Files you own" is not yours**, whether or not it is named here. If you
change, add or delete a file you do not own, Ocoder refuses the whole run and none of your work is
kept. `pnpm run verify` checks this first and names each file, so run it before you finish; restore
any file it names exactly as it was.

- `.storybook/preview.tsx`. It applies the providers and the app's global styles to every story.
  What you want to add there goes in `.storybook/providers.tsx`, which wraps every story and is
  yours: a global wrapper, a context, a default. Parameters for one component go in its story.
- `.storybook/main.ts`, `.storybook/target.json`, `package.json`, `pnpm-lock.yaml`,
  `pnpm-workspace.yaml`, `verify.mjs`, `catalog-check.mjs`, `ownership-check.mjs`, `ocoder.json`,
  this file.
- Story files may be edited but not deleted. Files under `fixtures/` may be added and removed.
- In `catalog.json`: the `component_key`, `source_binding` and `storybook_story_id` of existing cases,
  and the `target_id`, `viewport` and `themes`.
- Anything outside this folder. The application's source is read-only.

No packages can be installed: dependencies were installed before you started, and the network is
closed. If a component needs a package that is not installed, say so in your final message and leave
that story failing rather than working around it.

When a component cannot be rendered in isolation at all, leave its case failing and say why in your
final message. Do not delete the case.
